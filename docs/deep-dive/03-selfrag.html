③ Self-RAG 反思循环（LangGraph 显式状态机）

源码：src/insurwiki_rag/selfrag/graph.py（234 行）。入口 SelfRAGGraph.ask(query)，被 POST /api/chat 调用。Self-RAG 论文的四个反思 token（[Retrieve?] [IsRelevant?] [IsSupported?] [IsUseful?]）在本项目里是确定性的 Python 逻辑而非让 LLM 输出 token——可控、零额外调用、可回放。

1. 状态机与条件路由

stateDiagram-v2 [*] --> retrieve retrieve --> grade_relevant grade_relevant --> generate : relevant 非空 grade_relevant --> rewrite : relevant 为空 rewrite --> grade_relevant : 改写成功(内联重检索后) → 重新过相关性判定 rewrite --> [*] : 改写后仍无 / 已重试 → refused generate --> grade_supported grade_supported --> compliance : 支撑率≥0.35 grade_supported --> compliance : 支撑率<0.35 → 拒答改写 compliance --> grade_useful grade_useful --> [*] 
// 条件边的真实实现（_build 方法）
"grade_relevant": lambda s: "rewrite" if not s.get("relevant") else "generate"
"rewrite":        lambda s: END if s.get("refused") else "grade_relevant"

注意两个防环设计：改写循环只允许一次（retried 标志位），且改写重检索后回到 grade_relevant 重新判定，新候选不能免检；grade_supported → compliance 无条件边——低支撑率不回炉重生成，而是直接把答案替换为标准拒答话术（金融场景宁可拒答不可误导）。入门讲解见 新人图解指南。

2. 逐节点输入输出

节点① retrieve

输入 state：{"query": "等待期出险能赔吗"}。若 kg 已加载，先做图谱查询（见④）拿 graph_evidence，其 chunk_ids 作为第三证据通道传入检索：self.retriever.search(q, top_k=15, top_n=6, extra_channel=extra)。

输出 state 增量（真实结构）：

{
  "retrieve_decision": "[Retrieve?] yes",          // 无候选则 "[Retrieve?] no" + refused=true
  "candidates": [ /* 6 个 chunk，结构见② */ ],
  "graph_evidence": {"linked_entities": ["等待期"], "chunk_ids": ["c-9c02..."], "triples": [...]},
  "reflection": [{"token": "[Retrieve?]", "value": "[Retrieve?] yes",
                  "n_candidates": 6, "graph_linked_entities": ["等待期"]}]
}

检索返回空时直接置 refused=True、答案固定为"依据不足：知识库中未检索到……"，后续所有 LLM 节点全部短路跳过——这是拒答的第一道闸。

节点② grade_relevant（[IsRelevant?]，无 LLM）

相关性判定是分数阈值而非 LLM 判断：rerank 分 > 0.3 或 RRF 分 ≥ 0.03 的候选算相关：

relevant = [c for c in cands if (c.get("rerank_score") or 0) > 0.3
            or (c.get("rrf_score") or 0) >= 0.03]

两个阈值对应两种信号：rerank 分是 cross-encoder 的绝对相关性（0.3 大约是"确实在讲这个主题"），RRF 0.03 ≈ 双路都进前 5（1/62+1/64≈0.032），兜住"reranker 偏冷但双路共识强"的候选。

节点③ rewrite（Retrieve-again 循环）

仅当 relevant 为空且未重试过才触发。输入 {"query": "猝死给不给钱"} → LLM 改写 system prompt："你是保险领域检索查询改写器。把用户问题改写为更适合检索的包含关键词的完整句子……" → 输出 {"rewrite": "被保险人突发急性症状身故，保险合同是否承担身故保险金给付责任", "retried": true}，随后内联回调 _node_retrieve 用新查询重检索。

节点④ generate（带引用生成）

输入：relevant 前 5 条证据拼成编号块，图谱三元组（若有）作为受限上下文：

证据：
[1] chunk_id=c-9c02fbfcf8（XX重疾险条款·第二十一条）
被保险人因在等待期届满后……

图谱证据（本体约束内，仅可引用，不得编造其外关系）：
- 等待期 --约定期限--> 保险期间（被保险人在等待期届满后经指定医疗机…）

system prompt（原文）："你是严谨的保险条款助手。只依据给出的证据回答；引用证据时标注编号[n]；不得编造；若证据不足以回答，明确说'依据不足'。回答以「结论：」开头，先给结论再给条款依据。"

输出：state["answer"] = "结论：等待期内确诊不承担给付责任。[1] ……"

节点⑤ grade_supported（[IsSupported?]，支撑率算法核心）

这是 citation faithfulness 的代理指标——逐句答案-证据字符二元组（bigram）覆盖率，纯 Python 无 LLM：

  1. 答案按 (?<=[。；！？]) 切句；
  2. 全部证据拼成一个大字符串，收集其 bigram 集合 ev_bigrams；
  3. 每句计算 cover = 句内 bigram 落在 ev_bigrams 的比例，cover ≥ 0.5 记为"有支撑"；
  4. support_score = 有支撑句数 / 总句数，写入 reflection：{"token":"[IsSupported?]", "value":"0.83", "detail":"5/6 句有证据支撑"}。

逐句演算示例：答案句 "免赔额为人民币100元。" → bigrams {免赔,赔额,额为,为人,人民,民1,10,0元,...}。若证据原文含"免赔额……为人民币100元"，则"免赔/赔额/人民/民1..."等几乎全部命中，cover≈0.9 ≥ 0.5 → 该句有支撑。而幻觉句"保险公司将全额报销"中"全额/额报/报销"若不在任何证据里，cover 会跌到 0.2 以下 → 无支撑。

拒答阈值：support_score < SUPPORT_THRESHOLD(0.35) 时强制拒答，答案替换为："依据不足：现有条款证据对问题的支撑度较低（支撑率 X%，低于阈值 35%），为避免误导不作答……"。这是拒答的第二道闸（第一道是检索为空，第三道是 generate 的 useful 检查）。

为什么用 bigram 而不是词重叠：中文分词有边界歧义，二元字符组是分词无关的稳健词面度量，实现 3 行代码且可解释（每句给 x/y 计数）。

节点⑥ compliance（合规护栏）

  • 敏感词表 ["保证收益","稳赚不赔","绝对安全","保本保息","理赔全赔"] 命中则给答案追加警示（不删原文，保留审计痕迹）；
  • 无论是否拒答的正常答案都追加固定免责声明（DISCLAIMER，原文见源码 SENSITIVE_WORDS/DISCLAIMER 常量）；
  • 装配 citations：前 5 条 relevant → {chunk_id, n(条款号), policy(合同名), excerpt(前80字), scores:{rrf, rerank, from_graph}}，前端渲染成可点引用。

节点⑦ grade_useful（[IsUseful?]）

最终闸：useful = ("依据不足" not in answer) and len(answer) > 20。只是打标（写入 reflection 与最终 state），不再改变答案。

4. LLM 层的容错（llm.py 支撑细节）

  • Anthropic 兼容端点：POST {base}/v1/messages，头 x-api-key + anthropic-version: 2023-06-01，payload 显式 "thinking": {"type": "disabled"} 防止思考块吃掉 max_tokens；
  • 模型降级：glm-5.3 调用抛 LLMError（如 HTTP 1113）→ 自动切 glm-4.6 重试一次，并把 active_model 固化为降级模型（后续调用不再浪费一次失败）；
  • chat_json：在 system 尾部追加强制 JSON 指令 + _strip_fences 剥 ``` 围栏后 json.loads，供图谱抽取与意图分类复用。
