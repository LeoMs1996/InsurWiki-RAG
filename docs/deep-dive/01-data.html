2. 下载与解析（fetch / parse_instruction）

数据源是 InsQABench 合同问答训练集，经 hf-mirror.com 下载到 data/raw/insqabench_clause_train.json（已存在则跳过下载）。每条原始记录形如 {"instruction": "...", "output": "..."}，问答三元组全部埋在 instruction 自由文本里，用两个正则抠出来：

# data/pipeline.py
_RE_CONTRACT = re.compile(r"这段文字来自的合同是[:：]\s*(?P<name>.+?)\n")
_RE_FRAGMENT = re.compile(r"片段内容[:：]\s*(?P<frag>.*?)\n用户提问[:：]\s*(?P<q>.+)$", re.S)

示例：一步真实的输入 → 输出

输入（原始数据集中的一条）：

{
  "instruction": "这段文字来自的合同是：TaiPing太平财产保险有限公司恶性肿瘤住院医疗费用保险（互联网专属2021-B版）条款\n片段内容：第十三条 保险人按照第二十三条的约定，认为投保人、被保险人或者受益人提供的相关索赔的证明和资料不完整的，应当及时一次性通知……\n用户提问：如果保险人认为索赔证据不完整，会如何处理？",
  "output": "保险人会**一次性**通知投保人、被保险人或受益人补充提供。……"
}

输出（parse_instruction 返回的 dict；任一字段太短则整条丢弃：len(frag)<30 / len(q)<4 / len(output)<4）：

{
  "policy_name": "TaiPing太平财产保险有限公司恶性肿瘤住院医疗费用保险（互联网专属2021-B版）条款",
  "evidence": "第十三条 保险人按照第二十三条的约定，认为……",
  "question": "如果保险人认为索赔证据不完整，会如何处理？",
  "answer": "保险人会**一次性**通知投保人、被保险人或受益人补充提供。……"
}

3. 去重与采样（clean_and_sample）

去重不用整段文本，而是去空白后的 MD5 指纹：md5( question + "|" + evidence[:120] )——问题相同且证据开头相同即视为重复，避免标点/空白差异导致漏判。随后 random.Random(42) 固定种子采样，保证任何人重跑得到同一份 1500 条。

输入 31842 条解析记录 → 输出（data/processed/qa_triples.jsonl 第一行真实内容）：

{
  "qa_id": "qa-00014",
  "policy_name": "TaiPing太平财产保险有限公司恶性肿瘤住院医疗费用保险（互联网专属2021-B版）条款",
  "policy_id": "P6e27e96541",          // "P" + md5(合同名)[:10]，同名合同稳定同 ID
  "question": "如果保险人认为索赔证据不完整，会如何处理？",
  "answer": "保险人会**一次性**通知投保人、被保险人或受益人补充提供。……",
  "evidence": "第十三条 …… 第十四条 ……"
}

4. 按合同聚合成"文档"（build_corpus）

同一 policy_id 的所有证据片段（去重后）拼接成一份合同文档，供切分阶段拿到跨片段的条款上下文。输出 corpus_docs.jsonl：

{
  "doc_id": "doc-0000",
  "policy_id": "P00265f647b",
  "policy_name": "充电桩综合保险条款2020-01-18条款",
  "text": "<全部片段以 \n\n 连接>",
  "fragments": ["第十六条 ……", "第二条 ……", ...],   // 保持原文顺序
  "qa_ids": ["qa-00123", "qa-00456", ...]
}

5. 结构感知切分（chunk_docs → chunk_fragment）

保险条款是严格的条-款-项层级。切分器按四条规则保证语义完整性：

  1. 条边界：正则 第[一二三四五六七八九十百千零〇\d]+条 找出所有"第X条"位置，一个 chunk 永不跨条；
  2. 句边界聚合：条内按 (?<=[。！？；]) 切句，贪心装进窗口，超过 MAX_CHARS=420 就开新 chunk，并携带 OVERLAP_CHARS=60 的尾部重叠，防止边界句被截断丢上下文；
  3. 续条标记：同一条被切成多块时，后续块前缀 "第X条(续)"，让 embedding 与引用都能对回条款号；
  4. 表格独立通道：looks_like_table 命中（含"费率"+数字，或 |≥2，或 >60% 行含数字）的片段不走句子切分，整块走 table_to_kv 序列化为 Markdown 表 + KV 摘要，chunk_type="table"。

示例 A：普通条款切分

输入 fragment（doc-0000 的第一个片段，start_offset=0）："第十六条 保险人自收到赔偿保险金的请求和有关证明、资料之日起六十日内，……应当支付相应的差额。 投保人、被保险人义务"

输出（artifacts/index/chunks.jsonl 第一行，真实记录）：

{
  "text": "第十六条 保险人自收到赔偿保险金的请求和有关证明、资料之日起六十日内，……应当支付相应的差额。 投保人、被保险人义务",
  "section_path": "第十六条",           // 条款路径 = 条标题
  "offset": 0,                          // 在 doc.text 中的字符偏移，可回溯原文
  "chunk_type": "clause",
  "chunk_id": "c-3b2bb1986f",           // "c-" + md5(doc_id + text)[:10]，内容变 ID 即变
  "doc_id": "doc-0000",
  "policy_id": "P00265f647b",
  "policy_name": "充电桩综合保险条款2020-01-18条款"
}

同 doc 的第二个片段 offset=111 —— 即 0 + len(第一片段) + 2（2 是连接符 "\n\n"），偏移累计在 chunk_docs 中维护。

示例 B：表格通道序列化

输入（费率表片段，含 | 列分隔）：

年龄|费率
18-30|0.0025
31-40|0.0038

输出（table_to_kv，单 chunk、chunk_type="table"）：

（费率表/表格数据，Markdown 序列化）
| 年龄 | 费率 |
| 18-30 | 0.0025 |
| 31-40 | 0.0038 |

KV 摘要：
年龄：费率
18-30：0.0025
31-40：0.0038

Markdown 表给 reranker/LLM 看结构，KV 摘要给 BM25 提供词面命中（"18-30"“0.0025"这类 token 在表头行里很难被切词命中）。

6. 为什么这样设计（可核对的设计动机）

  • 420 字符窗口：注释原文"约等于 300 token（中文 1 字≈1.5 token 的保守值）"，同时低于 reranker 的 max_length=512，保证精排时不截断；
  • 60 字符 overlap：约 1~2 句，覆盖条款里"前句条件、后句结论"的高频句式；
  • chunk_id 内容寻址（md5(doc_id+text)）：重跑 pipeline 时内容未变的 chunk ID 稳定，图谱节点挂的 chunk_ids 不会漂移；
  • offset 元数据：引用回溯时可以从 doc.text 精确定位原文，而不是只能给"相似片段"。
