1. 先回答你的三个问题（30 秒版）

Q1：混合检索的时候会用到 Self-RAG 吗？
不会。调用方向是反的——是 Self-RAG 调用混合检索，不是混合检索调用 Self-RAG。混合检索（retrieval/hybrid.py）是个"纯工具"：给它一个问题，它还你 6 条最相关的条款片段，仅此而已，它不懂反思、不懂拒答。Self-RAG 状态机（selfrag/graph.py）的第一个节点 retrieve 才是它的调用方。打个比方：混合检索是"查资料的实习生"，Self-RAG 是"拿着实习员的资料做质检的审核员"——实习生从不反过来指挥审核员。
Q2：混合检索会用到 Wiki 吗？
会，但是"被动"地用。Wiki 页面在离线建库阶段就已经被重新向量化、切成带 chunk_type=wiki 标记的特殊 chunk，混进了检索索引（wiki/sediment.py 的 augment_index_with_wiki）。所以线上检索时，BM25 通道和向量通道都可能命中某张 Wiki 页——对检索器来说它就是索引里的一份普通资料，检索代码里没有任何一行"去查 Wiki"的逻辑。另有一种主动读法，但只发生在顾问 Agent 的 wiki_lookup 工具里（直接读 wiki/index.json），不经过混合检索。
Q3：那整条链路到底是怎样的？
一句话版：问题 → /api/chat → Self-RAG 状态机 → 第一步 retrieve 里同时做图谱查询（第三通道）+ 混合检索（BM25+向量两路）→ RRF 融合 → 重排 → 反思判定 → 生成 → 支撑率检查 → 合规装配 → 返回。图谱在"检索内部"，Wiki 在"索引数据里"，Self-RAG 在"检索外面"包着整个流程。看不懂没关系，下面第 3–5 节用三张图一步步拆。
图谱也一样是"被动"参与：Self-RAG 的 retrieve 节点会先调 kg.query(问题) 做实体链接，把命中的图谱实体关联的条款 chunk 作为第三条检索通道并进 RRF 融合。也就是说：04 号文档讲的 GraphRAG，在 /api/chat 链路里的位置是"检索的一个通道 + 生成时的三元组约束"，它不是一个独立的问答入口。

2. 预备概念：三个比喻看懂再往下读

2.1 RAG = 让大模型"开卷考试"

大模型只知道训练语料里的通识，不知道你们公司这 1633 个图谱节点背后的保单条款。RAG（Retrieval-Augmented Generation）就是考试前先把相关资料翻出来垫在题目下面，让模型只依据资料作答。流程永远是：检索 Retrieve→生成 Generate。朴素 RAG 的问题：资料找错了它也硬答（幻觉）、答完了没人检查。金融场景不能接受，所以要加"自我检查"——这就是 Self-RAG。

2.2 LangGraph = 把流程画成"质检流水线"

selfrag/graph.py 用 LangGraph 把问答流程建成一张状态机：每个节点是一道工序（检索、生成、检查……），边是工序间的流转，条件边是质检岔路口（合格→下一道；不合格→返工或拒收）。好处：流程可视化、每一步的状态都能留痕回放（reflection 字段）、岔路口规则是确定性的代码而不是模型的即兴发挥。

2.3 反思 token = 质检员盖的章

Self-RAG 论文（Asai et al., ICLR 2024）的核心思想：让模型在流程里不断自问四个问题并留下标记——[Retrieve?] 需要检索吗、[IsRelevant?] 资料相关吗、[IsSupported?] 答案有依据吗、[IsUseful?] 答案有用吗。本项目用确定性 Python 规则替模型"盖章"（见第 7 节），每个章都写进返回 JSON 的 reflection 数组，这就是你能在问答页看到的"反思轨迹"。

6. 混合检索内部：三通道 → RRF 融合 → 重排（详细流程图）

Self-RAG 的 retrieve 节点对检索器只有一次调用 search(q, top_k=15, top_n=6, extra_channel=…)，但这次调用内部是三条通道并跑：

通道 A · BM25（词面）对问题分词后在全部 chunk 上做关键词倒排打分。擅长：条款号、专有名词精确命中
通道 B · 向量（语义）bge-small-zh 把问题和 chunk 都编码成向量，算余弦相似度。擅长：换个说法也能找到
通道 C · 图谱（结构）retrieve 节点先调 kg.query：实体名出现在问题里→取 1-hop 邻域→关联 chunk（≤8 个）整队作为第三份排名表。擅长：跨条款的关系问题
→
RRF 融合（k=60）每通道第 r 名得 1/(60+r) 分，同一 chunk 的分数相加后排序，取前 15。图谱通道不插队，只是同样权重地投票
→
Cross-Encoder 重排bge-reranker-v2-m3 把「问题+chunk 正文」成对喂进去重新精算相关性，仅保留前 6，写入 rerank_score。精但慢，所以只喂 15 个

6.1 RRF 手算一遍（30 秒）

问题里出现"犹豫期"。候选 chunk_107 在向量通道排第 2、BM25 通道排第 5、图谱通道排第 1：

score(chunk_107) = 1/(60+2) + 1/(60+5) + 1/(60+1)
                  = 0.0161  + 0.0152  + 0.0164  = 0.0477   ← 三通道都投它，基本锁头名

这就是 RRF 的哲学：不比绝对分数，只比"几个通道都认你"。免调权重、对分数量纲免疫。

6.2 Wiki 在这张图里的位置

通道 A 和通道 B 的语料是同一份索引，里面除了条款 chunk，还有离线阶段回灌的 chunk_type=wiki 页面摘要（每页截取 ≤1500 字）。所以问"犹豫期一般多久"时，完全可能召回《犹豫期》主题页——它比零散条款更浓缩。检索代码对此无感知，这就是"沉淀反哺检索"的闭环落点。图谱通道（C）命中的则永远是条款 chunk（图谱节点的 chunk_ids 只登记条款出处）。

7.1 状态机全图（真实路由，含两道防环闸）

7.2 七个节点逐个拆（对应 03 号页的"逐节点输入输出"）

1retrieve 检索

读：query（或 rewrite 后的问题）
做：先 kg.query 拿图谱通道，再 search(top_k=15, top_n=6, extra_channel)；候选为空 → 直接置 refused（第一道拒答闸）。
写：candidates、graph_evidence、反思 [Retrieve?] yes/no。
误区：它不只调检索器——图谱查询也发生在这里，别在 generate 里找图谱。

2grade_relevant 相关性质检

读：candidates 的分数。
做：规则过滤：rerank_score>0.3 或 rrf_score≥0.03 算相关。
写：relevant 列表、反思 [IsRelevant?] yes/no。
误区：这一步零 LLM 调用。用阈值而非 LLM 判定——可控、省钱、可回放。

3rewrite 查询改写（Retrieve-again）

做：LLM 把口语问题改写成关键词完整的检索句，置 retried=True，内联重跑 retrieve，然后回到 grade_relevant 复检；复检仍无 → 拒答。
写：rewrite、retried、反思 [Retrieve?] yes(rewrite)。
误区：改写不是无限重试。retried 标志保证只改一次，防止死循环烧钱。

4generate 生成

读：relevant 前 5 条（带编号）+ 图谱三元组前 6 条。
做：GLM 只依据证据作答，引用标 [n]，以「结论：」开头，明确说"依据不足"当证据不够。
写：answer。
误区：三元组进 prompt 是带约束的——"仅可引用，不得编造其外关系"。

5grade_supported 支撑率质检

做：把答案切句，每句拆成相邻两字对（bigram），算有多大比例出现在证据原文里；覆盖 ≥50% 的句子算"有支撑"，支撑率 = 有支撑句 / 总句数，< SUPPORT_THRESHOLD=0.35 → 拒答。
误区：这是"引用忠实度"的代理指标，纯字符串比对，不调 LLM，所以快且可复现。

6compliance 合规装配

做：敏感词检查（命中则附提示）+ 拼免责声明 + 装配 citations（top5：chunk_id / 条款号 / 80 字摘录 / rrf·rerank 分数 / from_graph 标记）。
写：citations。
误区：citations 的 from_graph:true 能看出该证据是图谱通道拉进来的。

7grade_useful 最后质检

做：答案长度 >20 字且不含"依据不足"才算 useful，写入反思 [IsUseful?] 后结束。
误区：它不再触发任何返工——前两道闸已经兜住了，这里是收官审计章。

7.3 支撑率手算示例（跟 03 号页的演算对得上）

假设答案切成 4 句，bigram 覆盖率分别为 0.9 / 0.7 / 0.52 / 0.3。前三句 ≥0.5 算支撑句，第四句不算：

支撑率 = 3/4 = 0.75 ≥ 0.35  → 放行（若只有 1 句达标：1/4 = 0.25 < 0.35 → 拒答并说明原因）

阈值可用环境变量 SUPPORT_THRESHOLD 覆盖（config.py:44，默认 0.35）。

8. 重讲 04 号页 · GraphRAG 与 Wiki 知识沉淀

8.1 为什么有了向量检索还要图谱？

问"免赔额影响哪些责任条款"时，相关内容散落在五份合同的不同章节里。向量检索找的是"长得像问题的句子"——它不知道"免赔额"和"责任条款"之间有一条明确的免除责任边。图谱反过来：它只存"谁——什么关系——谁"这样的三元组，天生擅长跨文档关系。所以本项目把两者并联（不是替换）成三条检索通道。

三元组长这样众安百万医疗险（保险产品）
--免除责任--→
1万元免赔额（费率因子）
边上还挂着 evidence 原文短句和 chunk_id 出处
→
问答时怎么用① 实体链接：实体名出现在问题里即命中
② 1-hop：沿边走一步收集邻居
③ 邻居的 chunk_ids（≤8）进检索第三通道，三元组（生成时 ≤6 条）进 prompt

8.2 本体约束 = 给 LLM 立的"白名单"（04 号页核心概念）

让 LLM 自由抽取实体关系，它会抽出"系统/模块/包含"这类 IT 词汇污染图谱。所以 kg.py 顶部写死了保险领域本体——实体只许 8 类、关系只许 8 种，抽取 prompt 明说"本体外的信息一律不抽"，抽取结果还要过一道代码校验（add_extraction），类型不在白名单直接丢弃。

8 类实体大白话
保险产品哪款保单（如"众安百万医疗险"）
责任条款 / 免责条款保什么 / 不保什么
费率因子影响价格的因素（免赔额、年龄档）
犹豫期买了能无条件退的窗口期
保额 / 期限赔多少 / 保多久
被保险人群体给谁保（未成年人/家庭单）
8 种关系大白话
承保责任 / 免除责任保这个 / 明确不保这个
适用费率价格受它影响
享有犹豫期适用这段反悔窗口
约定保额 / 约定期限赔多少 / 保多久
适用群体投保人范围
关联条款兜底关联关系

白名单是双向的：写入侧挡住垃圾（校验丢弃），生成侧写进 system prompt（"不得编造本体外的条款关系"）。

8.4 Wiki 知识沉淀闭环：从"碎 chunk"到"主题页"再"反哺检索"

动机：chunk 是给机器看的碎片，人需要"犹豫期""免赔额"这样的主题页。沉淀流水线用图谱当骨架聚类，LLM 当写作员，产物再回灌索引：

① 选主题按图谱实体聚类：只挑 mentions≥3（被 ≥3 个 chunk 提及）的实体，最多 24 个主题太冷门的实体不值得单开一页
→
② 喂两样东西该实体的图谱三元组（关系全景） + 关联 chunk 原文（条款证据）
→
③ GLM 聚合写作只输出 JSON：overview（80 字概述）、points（3–6 条，每条带条款号）、keywords（4–6 个）
→
④ 渲染成页固定模板 markdown：front-matter 元数据 + 概述 + 要点 + 关联条款小节 + 标签，落盘 artifacts/wiki/
→
⑤ 建索引index.json 登记 24 页（topic_id/标题/关键词/概述），供 API 与 wiki_lookup 检索
→
⑥ 回灌（点睛之笔）wiki_pages_as_chunks：每页正文截 1500 字、打 chunk_type=wiki 标记，重新向量化并入主索引
⟲ 闭环完成：下次任何一次混合检索（BM25 路 / 向量路）都可能命中这些 Wiki chunk——机器沉淀的知识反过来喂机器自己；同时 Agent 的 wiki_lookup 直接读 index.json 给人看完整页。

对应源码：wiki/sediment.py（cluster_by_entity:50 / generate_wiki_pages:68 / render_pages:99 / wiki_pages_as_chunks:148 / augment_index_with_wiki:170）。实盘产物：24 页，见 Web「Wiki 知识沉淀」页签。

9. FAQ：新人最常问的 8 个问题

问题答案
反思为什么不用 LLM 来判？论文里反思 token 由模型生成；本项目改成确定性规则（分数阈值、bigram 覆盖）。三个理由：结果可复现可测试；零额外 LLM 调用省钱提速；阈值一行环境变量就能调（如 SUPPORT_THRESHOLD）。
支撑率低为什么不回炉重新生成？重新生成大概率换个说法继续编。金融场景的取舍是宁可拒答不可误导——拒答文案还会提示用户"补充更具体的问题或查阅原合同"，把人引向正路。
Self-RAG 和 Agent 到底什么区别？Self-RAG：单轮、无记忆、固定七节点流水线、强质检、必给引用——适合知识问答。Agent：多轮会话记忆（max_turns=8）、意图路由、按需调五工具、SSE 流式、可 HITL 挂起确认——适合办事（算保费、查图谱、翻 Wiki）。两条链路共用同一套检索器、图谱与合规词表。
拒答是不是系统坏了？不是，拒答是特性。三道闸：①检索无候选 ②改写复检仍无 ③支撑率<0.35。评测里拒答率是一个正经指标——全盘照答的系统才危险。
reflection 轨迹去哪看？POST /api/chat 返回 JSON 的 reflection 数组；问答页签会把四个章（[Retrieve?]/[IsRelevant?]/[IsSupported?]/[IsUseful?]）渲染出来。
想调参数改哪里？config.py：SUPPORT_THRESHOLD=0.35（拒答线）、RRF_K=60（融合平滑度）、RERANK_TOP_N=5；selfrag/graph.py retrieve 里 top_k=15/top_n=6、相关判据 rerank>0.3 或 rrf≥0.03；kg.query 的 chunk≤8/triples≤12。都可用环境变量覆盖。
实体链接用子串匹配会不会太土？领域实体名（"犹豫期""1万元免赔额"）本身高度专有，问题里出现原文即命中，子串够用且零成本。上限截断（chunk≤8）保证极端命中（如"保险"）不冲垮检索。
图谱通道为什么只算"软加权"？它以同权重参与 RRF 投票而非硬插队——图谱命中但文本不相关时，重排阶段（cross-encoder 看的是正文语义）会把它压下去，双保险防"图谱说什么就是什么"。
